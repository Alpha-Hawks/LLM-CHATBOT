# MLRITM Student AI Assistant

A personalized academic assistant for **Marri Laxman Reddy Institute of Technology and Management
(MLRITM)**. A student signs in once with their authorized **Anvaya** account
([anvaya.mlritm.ac.in](https://anvaya.mlritm.ac.in/)) and the assistant answers from *that
student's* current-semester academic context.

> "What is my attendance?" · "Which subjects am I studying this semester?" ·
> "Who is my DBMS faculty?" · "Which subjects have low attendance?"

Powered by **Llama 2 7B** fine-tuned with **QLoRA (4-bit NF4)** and served via **GGUF Q4_K_M**,
over a **three-source architecture**:

1. **The student's Anvaya record** — attendance, subjects, internal marks, faculty, timetable,
   exams, results and backlogs for the signed-in student only, authorized in the backend and
   rendered with deterministic calculations so no figure is ever generated by a language model.
2. **Official institutional knowledge** — retrieval over MLRITM autonomous regulations
   (MLR20/MLR22), fee structures and scholarship criteria, with source citations.
3. **General assistance** — for everything that needs neither of the above.

When a question needs both — *"what should I do, my attendance is below the requirement?"* — the
answer shows the student's own figures and the college regulation side by side, clearly labelled
so the two are never confused.

---

## 🛠️ Tech Stack

- **LLM Base & Fine-Tuning:** Llama 2 7B Chat, Hugging Face `transformers`, `peft`, `bitsandbytes` (4-bit NF4), `trl` SFTTrainer.
- **Inference & Quantization:** GGUF `Q4_K_M` via `llama.cpp` / `llama-cpp-python` with GBNF grammar constraints.
- **Backend:** FastAPI (Python 3.11), Pydantic v2, Server-Sent Events (SSE) streaming.
- **Personalization:** Student Data Service → Profile Store → Context Engine → AI Response Engine (see below).
- **Security & Privacy:** Anvaya-issued identity (signed launch token or OpenID Connect), server-side sessions with hashed tokens, backend authorization, AES-256-GCM encryption of the stored academic snapshot, pseudonymous audit trail, DPDP Act 2023 consent.
- **Database:** SQLAlchemy async with SQLite (local zero-config) and PostgreSQL (production).
- **Frontend:** Responsive student dashboard PWA (HTML5, Tailwind CSS, Marked.js) + Embeddable Web Component floating widget (`<mlritm-chat-widget>`).
- **Testing:** `pytest` (91 tests), `httpx` `MockTransport` stand-ins for the identity providers and the Anvaya data API.

## 🚀 Quickstart Guide

### 1. Environment Setup

```bash
# Clone the repository
cd "LLM CHATBOT"

# Create and activate virtual environment
python -m venv venv
# On Windows:
.\venv\Scripts\activate
# On Linux/macOS:
source venv/bin/activate

# Install dependencies
pip install -r requirements.txt
```

### 2. Configure Environment

Copy `.env.example` to `.env`:
```bash
cp .env.example .env
```
*(The example is production-safe: `IDENTITY_PROVIDER="none"` and `STUDENT_DATA_PROVIDER="none"`, so personal records stay off until an official Anvaya integration is configured. For a local demo, see **Local development demo** below.)*

### 3. Generate Q&A Dataset & Semantic Chunks (Phase 2)

```bash
python data/clean_and_chunk.py
python data/generate_qa.py
```
This partitions 2,500 verified and paraphrased question-answer pairs into `data/qa_dataset/train.jsonl`, `val.jsonl`, and `test.jsonl` using document-level splitting.

## 🌐 Embedding the Widget in Anvaya ERP

To embed the floating chat advisor on Anvaya or any college webpage, add this single `<script>` tag:

```html
<!-- Add before closing </body> tag -->
<script src="http://localhost:8000/widget/widget.js" defer></script>
```

The widget automatically mounts a closed Shadow DOM custom element (`<mlritm-chat-widget>`) at the bottom right corner, ensuring that styles never conflict with Anvaya's portal layout.

The widget opens the chatbot from the same server its script was loaded from. When Anvaya renders the widget for a signed-in student it can pass a freshly minted launch URL so the chat opens already signed in:

```html
<mlritm-chat-widget launch-url="https://<chatbot-host>/api/v1/auth/launch?launch_token=..."></mlritm-chat-widget>
```

Anvaya is served over HTTPS, so the chatbot must be too (browsers block `http://` iframes on HTTPS pages). Adding the tag to Anvaya itself has to be done by the MLRITM IT Cell / ORGMAKER.

## 🔐 Anvaya Sign-In and Personalization

> **Integration status (checked 2026-09-20):** no official Anvaya / ORGMAKER integration mechanism
> (SSO, OIDC, signed launch, or data API) is publicly documented. See
> [docs/anvaya_integration_research.md](docs/anvaya_integration_research.md); the request to MLRITM
> is in [docs/anvaya_permission_letter.md](docs/anvaya_permission_letter.md). Until MLRITM /
> ORGMAKER supply a mechanism and credentials, sign-in and personal records stay disabled and the
> assistant answers general questions only. Everything below is wired and tested, and turns on by
> configuration alone.

Students never type a roll number or password into the chatbot, and the chatbot never reads
Anvaya's web pages. The pipeline for one question:

```
Student → "Login with Anvaya" → Anvaya verifies them and issues a signed identity assertion
   │
   ├─ Anvaya Auth          services/identity/          verifies the assertion, maps claims
   ├─ Session              services/sessions.py        hashed token, 20 min, single-use handoff
   ├─ Authorization        services/authorization.py   session + DPDP consent + record ownership
   ├─ Student Data Service services/student_data/      loads ONLY that student's record
   ├─ Profile Store        services/student_profile_store.py   AES-256-GCM snapshot, one row
   ├─ Sync Service         services/sync_service.py    refresh, staleness, semester changes
   ├─ Context Engine       services/context_engine.py  selects the few fields this question needs
   └─ AI Response Engine   llm/ai_response_engine.py   personal record + policy → one answer
```

**Every stage is a hard boundary.** The intent router and the language model choose only *which
category* of the student's own records to show; they never supply an identity, and authorization
runs in the backend before any record is loaded. Ownership is re-verified every time a record
crosses a boundary — when it arrives from the provider, when it is written to or read from the
store, and before it is returned — so a misbehaving data source cannot deliver Student B's record
to Student A.

### Current semester

The student's current semester comes from the authorized data: Anvaya's own value if it supplies
one, otherwise the highest semester across their registered subjects. It is never guessed from the
date or the year — if neither is available the assistant says so. Subjects, faculty, internal marks,
exams and assignments are all scoped to it, and when a sync reports a different semester the stored
context follows automatically.

### What reaches the language model

Only the fields a question actually needs, copied out by name:

| Question | Selected |
|---|---|
| "What is my attendance?" | attendance totals and the subject breakdown |
| "Which subjects have low attendance?" | only the subjects below 75% |
| "Who is my DBMS faculty?" | only the faculty entry for that subject |
| "Which subjects am I studying?" | the current semester's registrations |

The full record is never passed on, and the student key, session identifiers, tokens, table names
and column names never appear in the context — there is no identifier in it for a model to use to
ask for more. Retrieved knowledge-base passages are fenced as untrusted data that must never be
treated as instructions.

### Mechanisms ready to connect (enabled only by configuration)

| `IDENTITY_PROVIDER` | MLRITM / ORGMAKER must provide | Chatbot endpoints |
|---|---|---|
| `oidc` | OpenID Connect issuer URL, client ID/secret, registered redirect URI, and the claim that identifies the student | `GET /api/v1/auth/oidc/login`, `GET /api/v1/auth/oidc/callback` |
| `signed_launch` | A short-lived signed JWT per launch (`iss`, `aud`, `sub`, `iat`, `exp`, `jti`), the algorithm, and the verification key (public key / JWKS URL, or a shared secret) | `POST` or `GET /api/v1/auth/launch` (`launch_token`) |

With `oidc`, **Login with Anvaya** starts the sign-in itself. With `signed_launch`, Anvaya starts
it, and the button tells the student to open the assistant from inside Anvaya. `/api/v1/auth/config`
reports which applies (`sign_in_mode`). After either path the browser is redirected to
`/app/#handoff=<one-time code>`, which the page exchanges once, within 60 s, at
`POST /api/v1/auth/session/exchange`.

If the vendor offers something else, add an `IdentityProvider` in
`backend/app/services/identity/` that produces a verified `AuthenticatedIdentity`.

### Connecting the student records

`STUDENT_DATA_PROVIDER="anvaya_api"` enables a ready, read-only, server-to-server client. Point it
at the approved interface:

```bash
STUDENT_DATA_PROVIDER="anvaya_api"
ANVAYA_API_BASE_URL="https://<approved-api-host>"
ANVAYA_API_STUDENT_PATH="/v1/students/{student_key}/academic"   # must contain {student_key}
ANVAYA_API_AUTH_SCHEME="bearer"        # bearer | header | none
ANVAYA_API_TOKEN="<service credential issued to this assistant>"
```

The `{student_key}` comes from the verified Anvaya identity held in the session — never from the
browser, the question text or the intent router. Adapt `_map_profile()` in
`backend/app/services/student_data/providers.py` to the response documentation MLRITM provides;
it is the single place field names are mapped, and anything the response omits stays empty rather
than being filled with a plausible value. If the interface is a different shape entirely, implement
`StudentDataProvider` (only `get_profile()` is required) and register it in the same file.

Everything fails closed: an unrecognised or half-configured provider resolves to `"none"`, and a
stored snapshot is discarded if the configured source has changed since it was written.

### Student endpoints

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/student/profile` | identity, current semester, counts and freshness (drives the dashboard header) |
| `POST /api/v1/student/sync` | force a refresh from Anvaya |
| `GET /api/v1/student/record/{kind}` | one category — `attendance`, `subjects`, `marks`, `faculty`, `timetable`, `exams`, `results`, `assignments`, `profile` |
| `DELETE /api/v1/student/data` | erase the stored snapshot (DPDP Act 2023) |

All require a valid session **and** recorded consent, and every one is scoped to the session holder.

### When Anvaya cannot be reached

Nothing is fabricated. A recent snapshot is served and clearly marked as the last values
retrieved; with nothing stored, the assistant says the record is unavailable and points the
student to Anvaya. General MLRITM questions keep working throughout, and answers always state
whether they came from the student's record or from general college information.

### Local development demo

`ENVIRONMENT="development"` allows `STUDENT_DATA_PROVIDER="sample"` (clearly labelled sample
records, never presented as Anvaya data) and the launch simulator, which signs a token with a
secret that exists only in your local `.env`:

```bash
# .env: ENVIRONMENT="development", IDENTITY_PROVIDER="signed_launch", LAUNCH_TOKEN_ALGORITHMS="HS256",
#       LAUNCH_TOKEN_ISSUER / LAUNCH_TOKEN_AUDIENCE / LAUNCH_TOKEN_HMAC_SECRET (32+ bytes), STUDENT_DATA_PROVIDER="sample"
uvicorn backend.app.main:app --reload     # then open http://localhost:8000/app/ and press
                                          # "Login with Anvaya" (the dev simulator)
python scripts/dev_launch.py              # or mint a single-use launch URL directly
```

The simulator refuses to run outside development, and sample data is refused in production.

## ⚡ Live Anvaya Personal Details Integration (Dual-Mode)

Students can view their **current live academic records** (Attendance, Internal Marks, Exam Results, Fee Payments, Class Timetable, and Exam Schedule) directly from the chatbot, governed by a strict dual-mode architecture:

```
                  ┌────────────────────────────────────────────────────────┐
                  │              Student Query in Chatbot                  │
                  │   ("What is my attendance?", "Show internal marks")    │
                  └──────────────────────────┬─────────────────────────────┘
                                             │
                          ┌──────────────────▼──────────────────┐
                          │     Is ANVAYA_API_BASE_URL set &     │
                          │   feature endpoint path configured? │
                          └──────────┬───────────────────┬──────┘
                                     │ YES               │ NO (or Blank)
                                     ▼                   ▼
                      ┌───────────────────────┐   ┌───────────────────────────────┐
                      │    PRIMARY PATH       │   │         FALLBACK PATH         │
                      │       (API Mode)      │   │       (Deep-Link Mode)        │
                      ├───────────────────────┤   ├───────────────────────────────┤
                      │ • Server-side REST    │   │ • Zero external API calls     │
                      │   API call to vendor  │   │ • Zero data copied/stored     │
                      │ • Service Auth Header │   │ • Generates direct link to:   │
                      │ • Ephemeral RAM Cache │   │   https://anvaya.mlritm.ac.in │
                      │   (TTL <= 180s)       │   │   /App/StudentAttendance      │
                      │ • Scoped to roll no.  │   │ • Live portal renders data    │
                      └───────────────────────┘   └───────────────────────────────┘
```

### Configuration (`config/anvaya.config`)
All settings are centrally configured in `config/anvaya.config` (with corresponding environment variable overrides in `.env`):
- `ANVAYA_API_BASE_URL`: Base URL for vendor REST API. **If left blank, the chatbot runs in Fallback Mode immediately with zero code changes.**
- `ANVAYA_API_USE_SANDBOX`: Set to `true` to route API calls to `ANVAYA_API_SANDBOX_URL` for staging verification.
- `ANVAYA_API_AUTH`: `none` | `api_key` | `oauth2_client_credentials`.
- Per-feature read paths: `ANVAYA_PATH_ATTENDANCE`, `ANVAYA_PATH_MARKS`, `ANVAYA_PATH_RESULTS`, `ANVAYA_PATH_FEES`, `ANVAYA_PATH_TIMETABLE`, `ANVAYA_PATH_EXAMS`, `ANVAYA_PATH_PROFILE`.
- Per-feature deep-link templates: `ANVAYA_LINK_ATTENDANCE`, `ANVAYA_LINK_MARKS`, etc.

### Running in Fallback Mode (Zero Vendor Dependency)
Leave `base_url = ` blank in `config/anvaya.config`. The chatbot runs purely via authenticated deep-links:
- When students ask for attendance or marks, the assistant presents the exact deep-link into `https://anvaya.mlritm.ac.in/App/...`.
- No student records are copied or fetched, providing immediate utility while awaiting vendor API access.

### Running in API Mode (Primary Path)
When the vendor provides endpoints:
1. Enter `base_url` and credentials (`api_key` or `oauth2_client_credentials`) in `config/anvaya.config` or `.env`.
2. To test against staging, set `use_sandbox = true`.
3. If an API request times out or fails (500/404), the assistant shows a calm error message and offers the direct deep-link fallback.

### SSO Launch Button & Dev-Only Mock Launcher
- **Production:** Anvaya provides a launch button that signs an RS256 JWT assertion (`sub = roll_number`, `iss = anvaya.mlritm.ac.in`, `aud = mlritm-chatbot`, `exp <= 120s`, `jti`) and POSTs to `/api/v1/auth/launch`.
- **Development Testing:** In development (`ENVIRONMENT="development"`), test SSO tokens can be generated via:
  ```
  GET /api/v1/auth/dev-launch?roll=237Y1A1270
  ```
  *(This endpoint returns HTTP 404 in production and is strictly disabled outside development).*

### DPDP Act 2023 Compliance
- Live records are cached exclusively in RAM with TTL $\le 180$ seconds.
- Zero disk or database persistence of live attendance, marks, results, or fee details.
- Students can only query their own records. If a query names another student's roll number, it is politely declined.

## 🧠 QLoRA Fine-Tuning on Single 16 GB T4 GPU

The training pipeline in `training/train_qlora.py` is configured for Google Colab or Kaggle:
- **Quantization:** 4-bit NormalFloat (NF4) with double quantization.
- **LoRA Hyperparameters:** $r=16, \alpha=32$, dropout $0.05$.
- **Batch Size:** Per-device batch $2$, gradient accumulation $8$ (effective batch size $16$).
- **Memory Optimizations:** `paged_adamw_8bit`, gradient checkpointing.
- **Export Pipeline:**
  1. Merge adapter into FP16 base: `python training/merge_and_export_gguf.py`
  2. Quantize to GGUF `Q4_K_M` for CPU inference via `llama.cpp`.

## 🔒 Security & DPDP Act 2023 Compliance

- **No Passwords:** The chatbot never asks for, receives, or stores an Anvaya password; identity comes from Anvaya-signed assertions only.
- **Chatbot Sessions:** Random tokens, stored only as SHA-256 hashes, 20-minute lifetime, revoked on sign-out. Launch tokens and OIDC state are single-use.
- **Access Isolation:** Authorization runs in the backend before any record is loaded; every record's owner is checked at each boundary it crosses. The LLM never makes authorization decisions.
- **Minimum Necessary Data:** Only the fields a question needs leave the backend; the full record, the student key and all internal identifiers stay inside it.
- **Encryption at Rest:** The stored academic snapshot is AES-256-GCM encrypted, so a database file or backup alone does not expose attendance, marks or results. The service refuses to start with a real data provider while the published placeholder keys are still in place.
- **Transport:** `Cache-Control: no-store` on every API response, `X-Content-Type-Options`, `Referrer-Policy`, a `frame-ancestors` policy limited to the configured origins, and optional HTTPS enforcement with HSTS (`ENFORCE_HTTPS`).
- **Audit Trail:** Sign-in, consent, record access, synchronization and erasure are logged against a truncated SHA-256 of the student key — never the key, the question or the record contents.
- **Data Minimization & Erasure:** One row per signed-in student, holding only what the official interface released; `DELETE /api/v1/student/data` erases it on request.
- **Prompt Injection Defense:** Reference documents are isolated inside `<college_knowledge untrusted="true">` boundaries with an explicit instruction never to follow directions found inside them; figures are rendered deterministically from the authorized record rather than generated.
